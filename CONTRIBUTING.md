# Contributing to Shikai

Thanks for helping out. Shikai is an Android-only, read-only GitHub client built with Expo SDK 54 and React Native 0.81. This guide gets you from a fresh clone to an open PR.

## Before you start

Open an issue first for anything bigger than a small bug fix, so we can agree on the approach before you write code. Shikai never writes to GitHub: features that create, edit, or delete things on a user's account are out of scope.

## Setup

You need:

- Node 24 (what CI uses)
- JDK 17 and the Android SDK, set up as in the [React Native environment guide](https://reactnative.dev/docs/set-up-your-environment?platform=android)
- An Android emulator or a phone with USB debugging on

Expo Go won't work, because Shikai ships its own native module (`modules/shikai-security`). You build a dev client once and then iterate with Metro:

```bash
git clone https://github.com/<you>/Shikai.git
cd Shikai
npm ci
cp .env.example .env
npx expo run:android
```

The first build takes 5 to 10 minutes. After that, JS changes reload through Metro and you only rebuild after you change native code, config plugins, or `app.config.ts`.

### Signing in during development

Leave `.env` blank. On the sign-in screen, tap **Sign in with a token** and paste a [personal access token](https://github.com/settings/tokens) with `repo` and `read:user` scopes. The OAuth button needs the maintainer's GitHub App and OAuth proxy, which aren't public, so it won't work in your build.

Add `notifications` to the token's scopes if you're working on notifications or alerts.

### Things that behave differently in a debug build

- Root, debugger, and developer-options checks pass automatically, so emulators work.
- Sentry stays off when `EXPO_PUBLIC_SENTRY_DSN` is blank.
- You don't need `keystore/` or `SHIKAI_KEYSTORE_PASSWORD`. Those only matter for release builds, which the maintainer makes.

## Where things live

Read [`AGENTS.md`](AGENTS.md) first. It maps the folders, key files, and conventions. For deeper context:

- [`notes/ARCHITECTURE.md`](notes/ARCHITECTURE.md): data flow, token rules, background work
- [`notes/DECISIONS.md`](notes/DECISIONS.md): why things are the way they are. Read the matching entry before you undo something that looks odd.

A few rules that trip people up:

- Colors come from `useTheme()`. Never hardcode a color.
- Use `FlashList`, not `FlatList`, and `react-native-reanimated` for animation.
- Native and gradle changes go in a config plugin under `plugins/`. `android/` is generated by `npx expo prebuild` and is gitignored, so hand edits there get thrown away.
- TypeScript is strict. No `any`.
- Don't add a dependency without raising it in the issue or PR first.

## Before you open a PR

Run the same checks CI runs:

```bash
npx expo lint
npx tsc --noEmit
npx vitest run
```

Tests live in `lib/__tests__/`. Add or update tests for logic you change. For UI changes, test on a device or emulator and attach a screenshot or screen recording to the PR.

## Commits and PRs

- Branch off `main` in your fork.
- Use [Conventional Commits](https://www.conventionalcommits.org/) with a scope, such as `fix(search): keep the query after a rotation` or `feat(repos): show archived badge`.
- Keep each PR to one change. Two unrelated fixes make two PRs.
- In the PR description, say what changed, why, and how you tested it.

## Reporting security issues

Don't open a public issue for a security problem. Message [@atharvdangedev](https://x.com/atharvdangedev) on X instead.
